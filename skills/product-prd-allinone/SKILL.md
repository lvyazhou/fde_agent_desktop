# Product PRD All-in-One（产品需求文档 + 配图 一体化生成）

## Overview

一个**自足**的技能：根据**任意形式的输入**，一次产出一份完整的 **PRD（产品需求文档）** 及其**全部配图**，不依赖其他技能。

本技能内置了三件事，合三为一：
1. **PRD 文档**：功能清单 + 每个功能点的业务逻辑（这是 PRD 与"功能清单"的本质区别）。
2. **商务架构图**：白底深蓝商务风，调用 `image-generator` 生图脚本出 PNG（内联规范，见第 §A）。
3. **流程图 / 时序图**：手写 SVG（fireworks 风格）+ `rsvg-convert` 转 PNG（内联规范，见第 §B）。

> PRD ≠ 功能清单。功能清单只回答"有哪些功能"，PRD 还要回答"每个功能怎么运转"——即每一个功能点的业务逻辑（触发条件、处理规则、输入输出、异常边界）。功能清单是 PRD 的一个章节，不是全部。

**支持的输入形式（全部兼容，无限制）**：一句话产品概念 / 一段描述或会议纪要 / 需求文档（Word/PDF/Markdown）/ 产品原型（HTML+JS）/ 一组截图 / 一个目录路径 / 口头描述 + 问答补充。

**输出**：`{产品名} - PRD.md` + `images/`（architecture.png、flow-*.png）+（可选）`.docx`。

## When to Use

- 用户说：生成 PRD、写 PRD、产品需求文档、生成产品需求文档、写产品文档、生成功能清单、出功能清单、产品功能需求、出产品清单
- 用户提供任何形式的产品信息，要求输出正式的产品需求文档
- 用户描述了一个产品想法，要求整理成 PRD
- 用户指向某个目录或文件，要求"出一份 PRD / 产品文档"

## When NOT to Use

- 只是已有 Markdown 转 Word（用 `product-doc-to-word` / `md-export` 技能）
- 技术架构文档、API 文档（格式不同）
- 用户只想聊产品想法不要文档输出
- 用户只要一张独立的图（可用独立的 `business-architecture-image` / `fireworks-tech-graph` 技能）

## 全流程步骤

```
用户一句话触发（生成PRD / 生成功能清单）
    ↓
Phase 1: 信息采集（适配任意输入）
    ↓
Phase 2: 生成 PRD Markdown（功能点带业务逻辑，图片先占位）
    ↓
Phase 3: 配图（§A 架构图 + §B 流程图/时序图 → images/，回填相对路径）
    ↓
Phase 4:（可选）转 Word
    ↓
完成，告知用户文件路径（.md / images/ / .docx）
```

### Phase 1：信息采集

**目标**：从任意输入中提取功能信息**及每个功能点的业务逻辑线索**。

| 输入形式 | 采集策略 |
|----------|---------|
| 一句话/一段描述 | 直接理解意图，必要时追问补充（目标用户？核心模块？关键功能怎么运转？） |
| 需求文档（MD/Word/PDF） | Read 文档，提取业务背景、功能需求、用户角色、**业务规则/流程** |
| 产品原型（HTML/JS） | 读页面结构+导航+组件+JS 数据模型+**交互逻辑/校验规则**，梳理模块架构与业务逻辑 |
| 目录路径 | Glob 扫描文件结构，优先读 index.html / README / 需求文档 |
| 截图 | 读图片，识别页面布局、导航结构、功能区块、**表单字段与状态** |
| 会议纪要/对话记录 | 提取需求决策点、功能列表、优先级、**业务约束** |

**要提取的信息**：① 产品名 + 一句话定位；② 目标用户（角色）；③ 需求来源；④ 功能模块架构（一级→子模块→功能点）；⑤ 每模块业务场景与痛点；⑥ **每个关键功能点的业务逻辑线索**（触发/处理/输入输出/异常）；⑦ **关键业务流程**（端到端，用于画流程图）；⑧ AI 能力分布（如有）；⑨ **核心数据模型 + 字段级明细**（用于数据字典）；⑩ **非功能性约束**（性能/安全/权限/兼容等）。

**信息不足时**：只给一句话可追问 1-2 个关键问题（目标用户、核心模块、关键功能运转方式）；不要过度追问；推断不了的用行业通用规则做默认值并标注"（建议，待确认）"。

**写作规则**：
1. 每个功能模块前必须有 `> **需求场景**` 和 `> **解决的痛点**` 引用块。
2. **每个核心功能点必须有六维度业务逻辑表**（触发/处理/输入/输出/规则/异常）——这是 PRD 与功能清单的本质区别。
3. 处理逻辑用编号步骤写清顺序、判断分支和规则，不能写"系统自动处理"这种空话。
4. **配图统一用本技能内置能力（§A/§B）生成，不手写 mermaid/ASCII**；图片存文档同级 `images/`，Markdown 用相对路径 `![说明](images/xxx.png)`。
5. 不写代码块（PRD 面向产品/业务/开发三方读者）。
6. 数据字典脱敏、给类型/约束/真实感示例值。
7. 版本号新产品从 v1.0 开始；日期用当前日期。
8. 简单展示类功能点不强凑六维度；推断出的逻辑标注"（建议，待确认）"。

# §A 配图规范一：商务架构图（内置，替代 business-architecture-image）

用于"二、产品架构总览"。调用 `image-generator` 生图脚本出图，**不要手画 SVG**。

## A.1 固定视觉合同（铁律）
- 画布 `1792x1024`；质量 `high`（网络慢时可降 `medium` 加速）。
- 背景白色或极浅灰蓝。
- **只用**深蓝、藏青、钢蓝、浅灰蓝、白色。
- **严禁**红、黄、橙、金、紫、暖色、霓虹、发光渐变。
- 气质：庄重、端正、克制、专业，适合管理层正式汇报。
- 不要人物、营销海报、赛博朋克、游戏 UI、复杂纹理、装饰性光球。
- 所有模块用白底卡片、细深蓝边框、统一圆角与一致间距。

## A.2 布局：按 PRD 的真实架构组织（不套固定模板）
- 顶部放完整标题（用户/PRD 原文，不缩写）。
- 按 PRD "产品架构总览"里的真实分层来画：通常是自下而上的 N 层（如 数据源层 → 数据汇聚治理层 → 能力层 → 应用层），每层一张等宽白底卡片，用贯穿各层的深蓝纵向主轴连接，数据流自下而上（层间加箭头）。
- 层内模块等宽对齐、均匀填充，不留大块空白。
- **内容保真**：PRD 里的层级名、模块名、系统名、专有名词原样写入提示词，不为"好看"改写或删减。

## A.3 Prompt 组装骨架
把 PRD 架构内容填进骨架，不要只写"做一张商务架构图"：

```text
白色背景，庄重严肃商务风格，适合企业管理层正式汇报。全图只用深蓝、藏青、钢蓝、浅灰蓝、白色，绝不用红黄橙金紫暖色和霓虹光。画布1792x1024，内容均匀填充，模块等宽对齐，左右密度均衡，无大块空白。所有模块为白底卡片、细深蓝边框、统一圆角。

顶部完整标题：{产品名 · 产品架构}

一张 {N} 层{产品域}架构图，自下而上 {N} 层，每层是一张独立等宽的白底深蓝边框横向卡片，用贯穿各层的深蓝纵向主轴连接，数据流自下而上：
第一层（底部）{层名}：{模块1 模块2 …}；
第二层 {层名}：{模块…}；
…
第 {N} 层（顶部）{层名}：{模块…}。

极简扁平商务风，无人物无装饰，所有文字使用中文标签。
```

## A.4 调用命令
脚本路径按当前环境的 image-generator 位置调整（常见：`~/.product-lobster/skills/image-generator/generate_images.py` 或本技能库同级的 `image-generator/generate_images.py`）。

```bash
PYTHONIOENCODING=utf-8 python3 {image-generator路径}/generate_images.py \
  -p "{组装后的完整中文提示词}" \
  -s 1792x1024 -q high \
  -d "{文档目录}/images" -o architecture.png
```

- 尺寸必须是 16 的倍数（1792x1024 合规）。
- 显式带 `-q high`（或 medium）；不传 quality 可能触发代理 bug。
- 脚本内置 API endpoint 与 key，无需额外配置。
- high 质量可能较慢；超时就降 medium 后台重试。

## A.5 生成前检查
- [ ] 标题与 PRD 原文一致
- [ ] 画布 1792x1024
- [ ] 只有深蓝系，无红黄橙金紫暖色
- [ ] 层级顺序、模块名与 PRD 架构一致，未擅自增删层
- [ ] 各层卡片等高、对齐、内容均衡

## A.6 常见失败与修正
| 失败 | 修正 |
|---|---|
| 没有标题 | 开头单独写"顶部完整标题：…" |
| 一边空一边满 | 写"等高卡片、等宽模块、边缘对齐、密度均衡" |
| 出现红/黄/金色 | 开头和结尾各写一次禁用色约束 |
| 擅自增加层级 | 写"共 N 层，不得增加其他层级" |
| 模块名被改写 | 写"用户提供的名称必须原样保留" |
| 变成赛博朋克 | 同时写"白底商务咨询报告风格"和"无霓虹无发光无复杂纹理" |

> 生图模型对中文小字、精确连线、模块数量可能偏差。生成后让用户重点检查标题、层级名、模块名；未经确认不要把生图替换进最终交付。

# §B 配图规范二：流程图 / 时序图（内置，替代 fireworks-tech-graph）

用于"三、核心业务流程"。**手写 SVG**（不依赖模板脚本），再用 `rsvg-convert` 转 PNG。业务流转用 flowchart，跨角色/接口交互用 sequence 时序图。

## B.1 风格令牌（fireworks flat 风）
- 画布白底：`<rect width fill="#ffffff"/>`；viewBox 按内容高度设，flowchart 常用 `0 0 960 700`（高栈用 760+），sequence 高度 = 80 + 消息数×50。
- 字体：`-apple-system, BlinkMacSystemFont, 'Segoe UI', 'PingFang SC', sans-serif`（含中文 fallback）。
- 主色深蓝 `#2563eb`（连线/箭头）；文字 `#1e293b`，次要文字 `#475569`。
- 节点填充/描边配色：
  - 起止（圆角胶囊）：fill `#dbeafe` stroke `#1d4ed8`
  - 处理（圆角矩形）：fill `#eff6ff` stroke `#2563eb`
  - 判定（菱形 polygon）：fill `#e0e7ff` stroke `#4338ca`
  - AI 能力节点：fill `#e0f2fe` stroke `#0369a1`（把 AI 步骤视觉区分出来）
- 箭头 marker：`<marker id="arrowBlue">` + `<polygon points="0 0,10 3.5,0 7" fill="#2563eb"/>`。
- 判定分支在连线旁标"是/否"及条件；闭环/回流用虚线 `stroke-dasharray="5,4"`。
- 左下角放小图例（起止/处理/判定/AI 能力色块 + 文字）。
- 节点标签短（≤6 字），细节放 sub-label 小字。

## B.2 SVG 骨架（可直接改写）
```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 960 700">
  <defs>
    <marker id="arrowBlue" markerWidth="10" markerHeight="7" refX="9" refY="3.5" orient="auto">
      <polygon points="0 0, 10 3.5, 0 7" fill="#2563eb"/>
    </marker>
  </defs>
  <style>
    text { font-family: -apple-system, BlinkMacSystemFont, 'Segoe UI', 'PingFang SC', sans-serif; }
    .title { font-size: 24px; font-weight: 700; fill: #1e293b; }
    .node-label { font-size: 14px; font-weight: 500; fill: #1e293b; }
    .decision-label { font-size: 13px; font-weight: 500; fill: #1e293b; }
    .arrow-label { font-size: 11px; fill: #475569; }
    .proc { fill:#eff6ff; stroke:#2563eb; stroke-width:1.5; }
    .startend { fill:#dbeafe; stroke:#1d4ed8; stroke-width:1.5; }
    .decision { fill:#e0e7ff; stroke:#4338ca; stroke-width:1.5; }
    .ai { fill:#e0f2fe; stroke:#0369a1; stroke-width:1.5; }
  </style>
  <rect width="960" height="700" fill="#ffffff"/>
  <text x="480" y="48" text-anchor="middle" class="title">{流程标题}</text>
  <!-- 节点：<rect class="proc" .. rx="8"/> 起止 rx=23 胶囊；判定用 <polygon class="decision" points=".."/> -->
  <!-- 连线：<line .. stroke="#2563eb" stroke-width="1.5" marker-end="url(#arrowBlue)"/>；回流加 stroke-dasharray="5,4" -->
  <!-- 图例：左下角 4 个色块 + 文字 -->
</svg>
```

## B.3 时序图（sequence）要点
- 参与者为顶部标签 + 垂直虚线 lifeline；消息为参与者间水平箭头，自上而下按时间排序。
- 激活期用 lifeline 上的细填充矩形；`loop/alt` 用带左上角标签的 `<rect>` 框住。

## B.4 校验 + 转 PNG
```bash
# 校验语法（无输出即通过）
rsvg-convert flow-1.svg -o /dev/null

# 转 PNG（-z 2 或 -w 1920 提升清晰度）
rsvg-convert -z 2 flow-1.svg -o flow-1.png
```
- 依赖 `rsvg-convert`（librsvg）。缺失时：macOS `brew install librsvg`；Debian/Ubuntu `apt install librsvg2-bin`。
- SVG 源文件保留在 images/（便于后续微调重出 PNG），Markdown 引用 PNG。

## B.5 降级
若 `rsvg-convert` 装不上，SVG 仍可直接嵌入 Markdown/浏览器查看；或退回该流程的文字说明并注明"（流程图见 SVG 源文件）"，不阻塞 PRD 产出。

## 核心规则（汇总）

### 内容质量
- 需求场景写具体业务场景（谁+何时+想做什么+现状痛点），不写空话。
- **业务逻辑是 PRD 核心**：处理逻辑编号、写清分支与规则；异常边界列失败场景及处理。
- 功能说明具体到可实现粒度，不用"支持XX功能"这种笼统描述。
- 痛点用"现状→目标"。数据字典/附录数据脱敏但有真实感。
- 无法确定的业务逻辑用行业通用规则推断，标注"（建议，待确认）"。

### 结构完整性
- 必含：需求概述 + 产品架构（配架构图）+ 核心业务流程（配流程图）+ 功能模块（每个核心功能点含业务逻辑）+ 页面交互 + 数据字典 + 非功能需求 + 需求对照 + 演进 + 附录；含 AI 时加 AI 能力分布。
- 每个功能模块有需求场景引用块；每个核心功能点有业务逻辑表；需求对照覆盖所有需求点。

### 原型解读要点
- 导航结构 → 功能模块划分；页面组件 → 具体功能点；JS 逻辑（校验/计算/状态机）→ 业务逻辑表的处理逻辑与约束；表单 → 输入字段与数据字典；AI 代码 → AI 能力嵌入位置；配置文件 → 产品元信息。

## 常见问题

**Q: 只给了一句话怎么办？**
A: 理解方向，追问 1-2 个关键信息（目标用户、核心模块、关键功能怎么运转），基于行业经验推断完整功能架构与业务逻辑，推断部分标注"（建议，待确认）"。不要过度追问。

**Q: 每个功能点业务逻辑写多细？**
A: 以"开发拿着能直接写代码、测试能直接写用例"为标准。核心功能点写全六维；简单展示类写"功能概述 + 一行说明"。

**Q: 业务流程图画几个？架构图几张？**
A: 核心端到端流程 2-4 个（§B）；架构图通常 1 张（§A）。

**Q: 画图环境依赖不全怎么办？**
A: 架构图靠 image-generator（内置 key，需 python3 + requests）；流程图靠 rsvg-convert（librsvg）。缺失按 §A.4 / §B.4 的安装命令装；实在装不上按 §B.5 降级，不阻塞 PRD 文档产出。

**Q: 输出文件放哪里？**
A: 优先用户指定路径；其次输入文件同级；口头输入无关联目录则询问。建 `产品文档/{产品名}/` + `images/`。
