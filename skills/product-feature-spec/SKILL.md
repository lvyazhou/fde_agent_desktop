# Product Feature Spec（产品功能清单生成）

## Overview

根据**任意形式的输入**，生成标准化的产品功能清单（.md + .docx）。

**支持的输入形式（全部兼容，无限制）**：
- 一句话产品概念（如"做一个医院排班系统"）
- 一段产品描述或会议纪要
- 一份需求调研文档（Word/PDF/Markdown）
- 产品原型文件（HTML 页面 + JS + 配置）
- 一组截图
- 一个目录路径（我自动扫描里面的文件）
- 用户口头描述 + 问答补充

**输出**：标准化的产品功能清单（.md + .docx）

## When to Use

- 用户说：生成产品功能清单、产品功能需求、写产品文档、出产品清单、出功能清单、写功能清单
- 用户提供了任何形式的产品信息，要求输出正式的产品功能清单
- 用户描述了一个产品想法，要求整理成文档
- 用户指向某个目录或文件，要求"出一份产品文档"

## When NOT to Use

- 只是已有 Markdown 转 Word（用 `product-doc-to-word` 技能）
- 技术架构文档、API 文档（格式不同）
- 用户只想聊产品想法不要文档输出

## 全流程步骤

### Phase 1：信息采集（适配任意输入）

**目标**：从用户提供的任意形式输入中提取产品功能信息。

**按输入形式选择策略**：

| 输入形式 | 采集策略 |
|----------|---------|
| 一句话/一段描述 | 直接理解意图，必要时追问补充（目标用户是谁？核心模块有哪些？） |
| 需求文档（MD/Word/PDF） | Read 文档，提取业务背景、功能需求、用户角色 |
| 产品原型（HTML/JS） | 读取页面结构+导航+组件+JS 数据模型，梳理模块架构 |
| 目录路径 | Glob 扫描文件结构，优先读 index.html / README / 需求文档 |
| 截图 | 读取图片，识别页面布局、导航结构、功能区块 |
| 会议纪要/对话记录 | 提取需求决策点、功能列表、优先级信息 |

**采集要输出的信息（无论哪种输入）**：
1. 产品名称 + 一句话定位
2. 目标用户（角色列表）
3. 需求来源/依据
4. 功能模块架构（一级模块 → 子模块 → 功能点）
5. 每个模块的业务场景和痛点
6. AI 能力分布（如有）
7. 核心数据模型（如有）

**信息不足时**：
- 如果用户只给了一句话，可以追问 1-2 个关键问题（目标用户、核心功能模块）
- 但不要过度追问——能推断的就推断，保持流程流畅
- 推断不了的用合理默认值，用户后续可修改

### Phase 3：转换为 Word 文档

**目标**：将生成的 Markdown 转为正式排版的 Word 文档。

**直接调用 `product-doc-to-word` 技能的规则**，核心排版规范：

| 元素 | 字体 | 字号 | 其他 |
|------|------|------|------|
| 一级标题 | 黑体 | 22pt | 加粗，居中 |
| 二级标题 | 黑体 | 16pt | 加粗，左对齐 |
| 三级标题 | 黑体 | 14pt | 加粗，左对齐 |
| 四级标题 | 黑体 | 12pt | 加粗，左对齐 |
| 正文 | 仿宋 | 12pt（小四） | 行距1.5倍，首行缩进两字符 |
| 元信息行 | 仿宋 | 10.5pt（五号） | 居中 |
| 表头 | 黑体 | 10.5pt | 加粗，蓝灰底色 #D9E2F3 |
| 表格正文 | 仿宋 | 10.5pt | 功能列加粗 |
| 英文/数字 | Times New Roman | 同中文 | eastAsia 设置 |
| 页边距 | — | — | 上下2.54cm，左右3.17cm |

**操作**：生成 python-docx 脚本 → 执行 → 输出 .docx 文件（与 .md 同目录同名）

## 核心规则

### 内容质量
- **需求场景**必须写具体业务场景（谁+什么时候+想做什么+现状痛点），不能写空话
- **功能说明**必须具体到可实现粒度，不能用"支持XX功能"这种笼统描述
- **痛点对比**用"现状→目标"格式，让读者一眼看到价值
- 附录数据要有真实感（具体数字、具体名称），但要脱敏

### 结构完整性
- 必须包含：需求概述 + 产品架构 + 功能模块（含需求场景）+ AI 能力分布 + 需求对照 + 演进方向 + 附录
- 每个功能模块必须有需求场景引用块
- 需求覆盖对照表必须覆盖所有需求点

### 产品原型解读要点
- 从导航结构看功能模块划分
- 从页面组件看具体功能点
- 从 JS 逻辑看数据模型和业务规则
- 从 AI 相关代码看 AI 能力嵌入位置
- 从配置文件看产品元信息（名称、版本）

### Word 转换要点
- 引用块（需求场景）在 Word 中转为仿宋正文段落
- ASCII 架构图在 Word 中忽略（或转为文字概述）
- 表格中的 emoji（✅）保留原样
- 脚本必须可执行，路径用绝对路径

## 常见问题

**Q: 用户只给了一句话怎么办？**
A: 先理解产品方向，追问 1-2 个关键信息（目标用户、核心模块），然后基于行业经验推断合理的功能架构，生成完整文档。不要过度追问。

**Q: 用户给了一份需求文档怎么办？**
A: 读取文档，提取需求要点，按模板结构重新组织为产品功能清单。需求文档中没有覆盖的部分（如痛点分析、AI 能力分布）基于上下文推断补充。

**Q: 有产品原型文件怎么办？**
A: 扫描目录结构，读取 HTML（页面架构）+ JS（数据模型/业务逻辑）+ 配置文件（产品元信息），提取完整功能点。

**Q: 功能清单要写多细？**
A: 以"产品经理拿着这份文档能和开发对齐需求"为标准。每个功能点一行表格，说明具体到可理解可实现。

**Q: 需求覆盖对照表怎么填？**
A: 如果有明确的需求文档，逐条对照；如果没有，按功能模块自行归纳需求要点。状态统一写"✅ 已覆盖"。

**Q: 输出文件放哪里？**
A: 文件必须写入当前工作目录（即 hermes session 的 cwd，对应项目目录 `~/.product-lobster/projects/<slug>/`）。不要写到 `~/.product-lobster/` 根目录。典型输出路径为 `./spec.md` 或 `./{产品名} - 产品功能清单.md`。
