# Product PRD（产品需求文档生成）

## Overview

根据**任意形式的输入**，生成一份完整的 **PRD（产品需求文档）**（.md + .docx）。

PRD ≠ 功能清单。**功能清单只回答"有哪些功能"，PRD 还要回答"每个功能怎么运转"**——即每一个功能点的业务逻辑（触发条件、处理规则、输入输出、异常边界）。功能清单是 PRD 的一个章节，不是全部。

**支持的输入形式（全部兼容，无限制）**：
- 一句话产品概念（如"做一个医院排班系统"）
- 一段产品描述或会议纪要
- 一份需求调研文档（Word/PDF/Markdown）
- 产品原型文件（HTML 页面 + JS + 配置）
- 一组截图
- 一个目录路径（我自动扫描里面的文件）
- 用户口头描述 + 问答补充

**输出**：一份完整的 PRD（.md + .docx）

## When to Use

- 用户说：生成 PRD、写 PRD、产品需求文档、生成产品需求文档、写产品文档、生成功能清单、出功能清单、产品功能需求、出产品清单
- 用户提供了任何形式的产品信息，要求输出正式的产品需求文档
- 用户描述了一个产品想法，要求整理成 PRD / 产品文档
- 用户指向某个目录或文件，要求"出一份 PRD / 产品文档"

## When NOT to Use

- 只是已有 Markdown 转 Word（用 `product-doc-to-word` 技能）
- 技术架构文档、API 文档（格式不同）
- 用户只想聊产品想法不要文档输出

## 全流程步骤

### Phase 1：信息采集（适配任意输入）

**目标**：从用户提供的任意形式输入中提取产品功能信息**及每个功能点的业务逻辑线索**。

**按输入形式选择策略**：

| 输入形式 | 采集策略 |
|----------|---------|
| 一句话/一段描述 | 直接理解意图，必要时追问补充（目标用户是谁？核心模块有哪些？关键功能怎么运转？） |
| 需求文档（MD/Word/PDF） | Read 文档，提取业务背景、功能需求、用户角色、**业务规则/流程** |
| 产品原型（HTML/JS） | 读取页面结构+导航+组件+JS 数据模型+**交互逻辑/校验规则**，梳理模块架构与业务逻辑 |
| 目录路径 | Glob 扫描文件结构，优先读 index.html / README / 需求文档 |
| 截图 | 读取图片，识别页面布局、导航结构、功能区块、**表单字段与状态** |
| 会议纪要/对话记录 | 提取需求决策点、功能列表、优先级信息、**业务约束** |

**采集要输出的信息（无论哪种输入）**：
1. 产品名称 + 一句话定位
2. 目标用户（角色列表）
3. 需求来源/依据
4. 功能模块架构（一级模块 → 子模块 → 功能点）
5. 每个模块的业务场景和痛点
6. **每个关键功能点的业务逻辑线索**（触发条件、处理步骤、输入输出、异常）
7. **关键业务流程**（端到端流转，用于画流程图）
8. AI 能力分布（如有）
9. **核心数据模型 + 字段级明细**（用于数据字典）
10. **非功能性约束**（性能、安全、权限、兼容性等，如有）

**信息不足时**：
- 如果用户只给了一句话，可以追问 1-2 个关键问题（目标用户、核心功能模块、关键功能的运转方式）
- 但不要过度追问——能推断的就推断，保持流程流畅
- 业务逻辑推断不了的用行业通用规则做合理默认值，并标注"（建议，待确认）"，用户后续可修改

### Phase 2.5：配图（调用画图技能）

**目标**：为 PRD 生成正式配图，替代手写 mermaid/ASCII。

**分工**：

|------|----------|--------|------|

| 三、核心业务流程 | `fireworks-tech-graph` | 流程图（flowchart）/ 时序图（sequence） | SVG + PNG |

**操作**：
1. 在文档目录下建 `images/` 子目录
2. 架构图：把模块划分、层级、数据流向组织成 `business-architecture-image` 的 prompt 骨架，出图存 `images/architecture.png`
3. 业务流程：每个核心流程（2-4 个）调用 `fireworks-tech-graph` 出图，业务流转用 flowchart、跨角色/接口交互用 sequence 时序图，存 `images/flow-{n}.png`
4. 回到 Phase 2 的 Markdown，把对应位置的图片占位替换为真实相对路径 `![说明](images/xxx.png)`

**降级**：若某个画图技能在当前环境不可用，退回该图的文字概述 + 一行说明，并在文档中注明"（配图待补）"，不阻塞 PRD 产出。

## 核心规则

### 内容质量
- **需求场景**必须写具体业务场景（谁+什么时候+想做什么+现状痛点），不能写空话
- **业务逻辑**是 PRD 的核心：处理逻辑必须编号、写清分支与规则；异常边界必须列出失败场景及处理
- **功能说明**必须具体到可实现粒度，不能用"支持XX功能"这种笼统描述
- **痛点对比**用"现状→目标"格式，让读者一眼看到价值
- 数据字典与附录数据要有真实感（具体数字、具体名称），但要脱敏
- 无法确定的业务逻辑用行业通用规则推断，并标注"（建议，待确认）"

### 结构完整性
- 必须包含：需求概述 + 产品架构 + 核心业务流程 + 功能模块（每个核心功能点含业务逻辑）+ 页面交互 + 数据字典 + 非功能需求 + 需求对照 + 演进 + 附录
- 含 AI 能力时增加 AI 能力分布章节
- 每个功能模块必须有需求场景引用块
- 每个核心功能点必须有业务逻辑表
- 需求覆盖对照表必须覆盖所有需求点

### 产品原型解读要点
- 从导航结构看功能模块划分
- 从页面组件看具体功能点
- 从 JS 逻辑看**数据模型和业务规则**（校验、计算、状态机 → 业务逻辑表的处理逻辑与约束）
- 从表单看输入字段、必填校验 → 数据字典与"输入"维度
- 从 AI 相关代码看 AI 能力嵌入位置
- 从配置文件看产品元信息（名称、版本）

### Word 转换要点
- 引用块（需求场景）在 Word 中转为仿宋正文段落
- **配图（架构图/流程图 PNG）**：Word 中作为图片居中插入（python-docx `add_picture`），路径用绝对路径，宽度适配页宽；配图下方加图题（如"图 3-1 接诊到开单流程"）
- 表格中的 emoji（✅）保留原样
- 脚本必须可执行，路径用绝对路径

## 常见问题

**Q: 用户只给了一句话怎么办？**
A: 先理解产品方向，追问 1-2 个关键信息（目标用户、核心模块、关键功能怎么运转），然后基于行业经验推断合理的功能架构和业务逻辑，生成完整 PRD。推断的业务逻辑标注"（建议，待确认）"。不要过度追问。

**Q: 用户给了一份需求文档怎么办？**
A: 读取文档，提取需求要点和业务规则，按 PRD 模板重新组织。文档没覆盖的业务逻辑（触发条件、异常处理）基于上下文与行业经验推断补充并标注。

**Q: 有产品原型文件怎么办？**
A: 扫描目录结构，读 HTML（页面架构）+ JS（数据模型/校验/状态机 → 业务逻辑）+ 配置（元信息），提取完整功能点及其业务逻辑。

**Q: 每个功能点的业务逻辑要写多细？**
A: 以"开发拿着这份业务逻辑能直接写代码、测试能直接写用例"为标准。核心功能点写全六个维度；简单展示类功能点写"功能概述 + 一行说明"即可，不强凑。

**Q: 业务流程图要画几个？**
A: 只画核心端到端流程，一般 2-4 个（如"下单流程""审批流程"）。调用 `fireworks-tech-graph` 出图（业务流转用 flowchart，跨角色/接口交互用 sequence 时序图），配一段流程说明。

**Q: 数据字典要写哪些实体？**
A: 只列核心业务实体（一般 3-8 个），字段级明细含类型、必填、约束、来源、示例。脱敏但有真实感。

**Q: 用户说"生成功能清单"而不是"生成 PRD"呢？**
A: 仍然生成完整 PRD（功能清单是 PRD 的功能模块章节）。如果用户明确只要精简的功能清单不要业务逻辑，可省略业务流程图、数据字典、非功能需求章节，功能点只保留"功能概述 + 一行说明"。

**Q: 输出文件放哪里？**
A: 优先放在用户指定的路径；其次放在输入文件同级目录；如果是口头输入没有关联目录，询问用户。
