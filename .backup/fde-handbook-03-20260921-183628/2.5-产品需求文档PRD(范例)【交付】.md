# 重庆永川医院体检报告解读智能体

> 产品需求文档（PRD·标准版）

## 一、需求概述

### 1.1 业务背景

重庆医科大学附属永川医院每年承接大批量单位团检、个人自费体检，体检人群基数持续增长，但检后报告解读服务存在严重供需失衡，成为体检服务链条的核心短板，患者、医院两端均存在明显痛点：

患者端

线下解读受时间和地点限制，患者缺少随时咨询具体报告疑点的渠道（P0，影响：体检患者）；

院内现有报告为标准化模板文字，专业生硬、缺少互动，老年患者使用门槛较高（P0，影响：老年患者、团检职工）；

医院端

专职解读人力缺口巨大，重复解释难以覆盖持续增长的体检人群，人工模式无法规模化落地（P0，影响：总检医生、体检服务团队）；

回答质量、患者反馈及人工分流效果缺少统一统计和追溯（P1，影响：医院管理与审计人员）。

### 1.2 产品目标

| 目标 | 衡量标准 |
| --- | --- |
| 提供 7×24 小时报告疑点辅助解释 | 入口可达率、身份校验成功率；实际使用率目标试点后确认。真人医生服务按医院实际服务时段提供 |
| 统一院内回答口径，降低重复咨询工作量 | 体检相关人工咨询量、医生节省时间；试点后评估，不预设下降比例 |
| 支持医生审核与问题追溯 | 案例标注覆盖率、审核与纠错记录完整性；灰度医学验收测试集及通过标准由院方确认 |
| 语音交互可用 | 普通话可用；重庆方言识别与播报效果阈值在 POC 前以 ASR 测试集确认 |
| 超范围问题正确分流 | 转介准确率、错误引导率；不以就诊转化为首要目标，关注超范围问题是否正确转线下/转真人 |
| 患者满意度 | 目标值在患者灰度测试（100—200 名）后确认 |

### 1.4 核心约束与非目标

核心约束

| 约束类型 | 具体约束 |
| --- | --- |
| 报告来源 | 一期默认对接院内体检系统读取本人报告，同时支持患者主动上传图片、拍照或 PDF 格式的第三方体检报告。上传文件须通过格式、文件安全、清晰度和内容完整性校验后解析；无法识别、非体检报告或内容不完整时不进入解读。身份校验接口由医院认可的身份平台提供。 |
| 医学边界 | 只解释报告已有结论与异常指标，不新增诊断、风险等级、用药或治疗方案。每条关键解读可追溯报告字段、知识/规则版本及生成时间 |
| 建议依据 | 进一步检查须来自报告原文、医生结论或审核规则；饮食及运动建议仅为审核后的低风险通用建议 |
| 安全兜底 | 急症、高风险症状、诊断、用药、超报告范围或低置信问题停止自由生成，提供院方确认的人工/就医指引。显著提示"AI 仅用于解释报告，医学判断以具备资质的医生意见为准" |
| 身份与权限 | 患者仅访问本人报告；总检医生按授权查看与标注；医院管理员不默认获得患者原始报告权限；运维按脱敏排障权限处理；数据管理员维护逻辑模型与授权；安全审计只读 |
| 数据安全与留存 | 身份信息与模型上下文分离；最小必要字段、统一脱敏、HTTPS/TLS 及访问审计。报告、问答与音频按医院制度留存，期限与删除策略由院方确认 |
| 语音范围 | 支持普通话和重庆话输入及播报；先生成回答，再由患者选择语言、内容并触发播报，不实时生成播报内容，不默认通读全报告。播报长度、语速及方言效果阈值待确认 |

非目标（明确不在本次范围内，防止范围蔓延）

| # | 非目标 | 原因 |
| --- | --- | --- |
| 1 | AI 进行新的医学诊断或推断 | 法律与医疗安全风险，本产品定位为"翻译官"而非"医生" |
| 2 | 直接接入 LIS/HIS | 一期仅对接院内体检系统读取本人报告，聚焦体检报告解释 |
| 3 | 提供用药建议或用药方案调整 | 超出"翻译转述"边界，涉及处方权 |
| 4 | 影像类报告（X 光/CT/MRI 图像）解读 | 多模态模型复杂度骤增，一期仅处理文本/数值类报告 |
| 5 | 除普通话、重庆方言外的其他方言 | 语料库建设成本高，先聚焦核心用户群；英语仅做 POC 验证 |
| 6 | 多次历史报告趋势分析 | 一期仅支持同类型、近两年内最多两份已出报告的双报告对比；不输出长期趋势。 |
| 7 | 对接第三方挂号平台（如微医、好大夫） | 一期优先使用本院咨询和挂号入口 |

暂缓范围：连续历史趋势、检后转诊、英语正式能力、其他方言、第三方挂号、影像图像解读、专病慢病及全病程管理不列入一期确定交付。

## 二、产品架构总览

说明：患者侧的报告查询、上传与双报告对比统一归入 A 模块；历史报告对比不再作为独立模块。

平台自下而上分四层：数据源层（院内体检系统、院方身份校验平台、真人医生会话服务、预约就诊资源）→ 数据接入与治理层（SeaTunnel 同步、Doris 数据底座、SDR/sdr-one 逻辑模型的统一鉴权脱敏、一致性校验）→ AI 能力层（报告疑点解释、上下文问答、普通话/重庆话语音识别与播报、敏感问法识别与安全兜底、一致性与置信度校验）→ 应用层（患者端 7 个模块 + 医院管理端 4 个模块）。全平台以"只解释报告已有结论、每条解读可追溯依据"为核心安全基线，安全与审计能力贯穿全链路。

产品架构图

架构说明

所有上层应用共享同一套经 SDR 逻辑模型鉴权脱敏后的报告数据，保证"患者只见本人报告、字段最小必要"。

AI 能力层不直接访问源库；Doris 不可用时明确提示、告警并以服务不可用兜底，不默认回查源库。

报告查询、身份校验、资源配置与数据同步属于系统基础功能，不作为 AI 能力；AI 能力聚焦解释生成、上下文问答、语音交互与安全识别分流。

## 三、核心业务流程

### 3.1 报告疑点解释与连续追问流程（患者主流程）

流程图

流程说明：患者经院方身份平台校验后进入报告列表，选择已出报告进入异常结果/报告摘要双视图；点击异常项获得固定三段式解读，并可围绕当前报告连续追问。回答前先经敏感问法识别，命中越界、高风险或低置信问题即停止自由生成并执行院方审核的固定提示与分流；正常问题则绑定报告上下文生成回答并展示依据，患者可按需触发语音播报并反馈有帮助/没帮助。关键分支：身份校验失败不返回任何报告内容；切换报告前需确认并进入独立会话，原报告聊天保留且不混用；多轮（阈值待确认）仍不理解时引导总检医生。

### 3.2 敏感问法识别与服务分流流程（安全兜底）

流程图

流程说明：患者端常驻“医生在线问诊”“智能导诊”“健康咨询”三个服务入口。选择医生在线问诊需二次确认，确认后同步当前报告与问题进入排队，由认证医生接诊，AI 不得冒充医生；医生离线时展示服务时间及替代指引。智能导诊基于报告已有就医建议匹配诊室，不主动新增科室推荐，匹配结果可追溯。健康咨询模式须先确认就诊范围，仅回答报告解释与审核后的通用健康管理问题，遇诊断、用药或明显症状问题立即中止并引导真人。关键分支：AI 提前识别诊断、用药、高风险症状及低置信问题并执行兜底，分流效果由院方安全测试集验证；全部医生停用时患者端展示替代指引。

### 3.3 医学审核与知识闭环流程（管理端）

流程图

流程说明：患者问答沉淀为案例后按置信度及审核状态组织，总检医生逐项查看原文、三段解读及依据，标注正确/需修改/禁答并打分完成审核；高置信自动免审规则须院方确认后才启用。术语库按科室、状态检索维护，经版本审核后发布，保留灰度与回滚能力。审核与发布结果反哺患者端回答口径，形成"试用 → 标注 → 审核 → 发布 → 反哺"的医学质量闭环。关键分支：禁答标注沿用原需求；版本流程沿用原需求，医生审核生效；上线前专业验收仍必需。

#### 4.2.3 权限原则与约束

最小必要：患者仅访问本人报告；模型仅获取完成本次解释所需的最少字段，身份信息与模型上下文分离。

越权拦截：身份校验失败或报告归属不符时不返回任何报告内容，越权访问全部拦截并进入审计事件。

医院管理员不默认获得患者原始报告权限；管理端统计数据默认聚合口径，查看明细需另经授权。

运维按脱敏排障权限处理，不接触明文敏感字段；敏感明文不入普通日志。

数据管理员仅维护逻辑模型、授权与同步，不直接消费报告内容；安全审计全量只读、不可修改。

AI 不得冒充真人医生；医生入口仅承接认证医生的真人会话。

#### 4.2.4 登录与身份校验

患者登录与身份校验接口由医院认可的身份平台提供，按院方认可身份要素校验本人及报告归属；演示账号及任意验证码不作为正式鉴权。

校验失败不返回报告内容，仅提示失败原因；退出登录后不可直接读取报告，需重新完成身份校验。

患者端实际入口与终端范围（小程序、App、Web）待院方确认，权限校验在各端保持一致。

## 五、数据对接

### 5.1 数据链路与接口

链路说明

SeaTunnel 将体检报告全量初始化后按日期增量同步至 Doris；SDR/sdr-one 封装逻辑模型，执行鉴权、授权、字段脱敏、限流与审计，智能体经统一服务获取报告，不直接访问源库。

同步低峰窗口、T+1/小时级时效由双方确认；按左闭右开时间窗口补数、重跑；完成数据量比对、关键字段抽样校验和失败重试，保留校验报告。

Doris 不可用时明确提示、告警并以服务不可用兜底，不默认回查源库；受控降级链路如需建设另行确认。

业务应用、模型、知识库、数据底座及日志原则上在院内或批准的本地资源池部署；云模型/云语音仅为另行审批的可选方案。
