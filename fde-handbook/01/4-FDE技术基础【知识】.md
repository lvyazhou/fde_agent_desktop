# FDE 技术基础：前端、后端、API、数据库、服务器

这篇是写给 FDE 和非技术岗同事的。目标不是让你会写代码，而是听到研发说“这是前端问题”“接口还没好”“数据库要改字段”时，你能知道他们在说什么，也知道该追问什么。

## 先用一个点餐的比方

把一个软件系统想成一家餐厅：

- **前端**是菜单、点餐界面、桌号牌这些你能看到的东西。
- **后端**是后厨，负责判断菜怎么做、能不能做、什么时候出餐。
- **API**是服务员，负责在前台和后厨之间传话，传的是双方约定好的内容。
- **数据库**是仓库和账本，记录食材、订单、会员信息。
- **服务器**是开店的地方，上面这些软件要在某台机器上运行。

比方到这里就行，别推得太细。软件比餐厅复杂，但这个关系先记住：**用户看到的是前端，真正做判断的多半在后端，中间靠 API 传数据，数据放在数据库，程序跑在服务器上。**

## 前端：用户看得见、点得到的部分

前端就是软件的“脸”。网页、App 页面、按钮、输入框、弹窗、列表、图表，都属于前端。你在产品原型里画的大部分界面，最后都要由前端实现。

它负责三件事：

1. 把界面画出来。
2. 接住用户的操作，比如点击、输入、滑动。
3. 把用户操作发给后端，再把后端返回的结果展示出来。

常见技术名字有 Vue、React、小程序、H5。你不用会写，但要知道：**页面长什么样、交互顺不顺，多半先看前端；业务规则对不对，多半往后端查。**

产品评审时，前端相关别只看“正常流程”。还要看：

- 数据加载中显示什么？
- 没有数据时显示什么？
- 网络失败、权限不足、后端报错时，用户看到什么？
- 用户连续点三次按钮，会发生什么？

这几个状态不提前想清楚，上线后就会变成一堆体验问题。

## 后端：看不见但做判断的部分

后端跑在服务器上，用户看不见它，但它承担了很多关键判断：

- 这个用户有没有权限看这份数据？
- 提交的金额、日期、状态合不合法？
- 库存够不够？名额有没有被别人抢走？
- 这条数据该写给哪个租户、哪个科室、哪个部门？
- 要不要调用 AI、发通知、写日志、触发下一个流程？

举个例子，用户点“提交请假申请”。前端只负责把表单发出去；后端要判断这个人存不存在、有没有审批权限、请假时间是否冲突、审批流走谁、最后把结果写进数据库。

常见技术名字有 FastAPI、Java、Node.js、Python 服务。说到底，你可以把后端理解成**业务规则的执行者**。前端可以长得很好看，但如果后端规则错了，业务照样跑偏。

## API：前后端之间的约定

API 不是一个页面，也不是一台机器，它是前后端之间的**接口约定**：前端发什么参数，后端回什么数据，双方先讲清楚。

比如登录接口，前端发送：

```json
{
  "username": "zhangsan",
  "password": "******"
}
```

后端可能返回：

```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "userId": "u_10001",
    "name": "张三"
  }
}
```

研发说“接口没好”，通常意思是：**这个约定还没定下来，或者后端还没把数据吐出来，所以前端拿不到真实数据。**

这里有个很关键的产品认知：改字段经常不是只改页面。比如把“手机号”改成“手机号 + 验证码登录”，可能要改数据库字段、改接口参数、改前端表单、改权限判断。看起来是小改动，实际牵扯前后端。

## 数据库：存数据的地方

数据库存的是结构化数据，可以想成很多张表：

- 用户表：用户 ID、姓名、手机号、部门、角色。
- 订单表：订单号、用户 ID、金额、状态、创建时间。
- 请假表：申请人、开始时间、结束时间、审批状态。

表和表之间有关联。比如订单表里的 `user_id` 会指向用户表里的某个人。研发常说的 ER 模型，本质上就是把“有哪些数据、字段是什么、谁跟谁有关”先画清楚。

FDE 要特别关心四件事：

- 这个功能到底要存哪些字段？
- 数据从哪里来，用户填、系统生成，还是第三方同步？
- 谁能看、谁能改、谁能删除？
- 数据要保留多久，能不能导出？

尤其在医疗、教育这类项目里，权限和数据来源不是小事，最好在需求阶段就问明白。

## 服务器：程序运行的地方

服务器就是一台一直开着的计算机，前端包、后端服务、数据库、AI 服务，都可能部署在上面。云端服务器放在云厂商机房，本地化部署则放在客户机房。

服务器和数据库不是一回事。服务器更像是“场地”，数据库是“账本”。小项目可以放在一起，正式项目通常会分开部署，方便维护和安全控制。

研发说“本地可以，线上不行”，通常是环境差异：账号配置、网络权限、数据库地址、版本没发上去，都可能导致问题。**本地能跑只说明程序没坏，线上能用还要看部署和配置。**

## 一次登录到底发生了什么

把前面的概念串起来看一次登录：

1. 用户在登录页输入账号和密码，这一页是前端。
2. 前端先做个简单检查，比如账号是否为空、密码长度够不够。
3. 检查通过后，前端通过 API 把账号密码发给后端。
4. 后端去数据库查这个用户是否存在，再校验密码和状态。
5. 校验通过后，后端生成登录凭证，返回给前端。
6. 前端保存凭证，跳转到系统首页。

这六步里，任何一步都有可能出问题：页面按钮点不了，是前端；密码校验规则错，是后端；查不到用户，可能是数据库；请求根本发不出去，可能是网络或部署配置。

## 常见误会

**“页面显示错了”不一定都是前端问题。**
前端只是展示结果。如果后端返回的数据本来就错，前端显示出来照样错。定位问题时要看接口返回了什么。

**“改个字段”经常不小。**
界面字段、接口字段、数据库字段是三件事。只改界面叫文案调整；改接口和数据库，就要考虑历史数据兼容。

**“接口通了”不等于“功能好了”。**
接口通了只说明数据能来回。数据对不对、权限严不严、异常情况处理没处理，还要另测。

**“用了假数据”很容易骗过验收。**
演示页面可以先写死数据，但真实上线要接真实数据源。验收时一定要问：现在看到的是 mock 数据，还是数据库真实数据？

**权限不是登录页的事。**
登录只是入口。每个页面、每个接口、每条数据，都可能有权限判断。尤其多租户系统，漏了隔离就是大事故。

## 常用语言和框架

先分清三个词：**语言、框架、组件不是一回事。**

- 语言是写代码用的语法，比如 JavaScript、Python、Java。
- 框架是在语言上封装好的一套开发方式，比如 Vue、React、FastAPI。
- 组件是已经做好的功能块，比如一个表格、一个上传框、一个登录模块。

研发嘴里的“技术栈”，就是把语言、框架、数据库、中间件这些选型合在一起说。

### 前端常用

| 名字 | 是什么 | 你听到时可以理解为 |
|---|---|---|
| HTML / CSS | 页面结构和样式 | 页面上有什么、长什么样 |
| JavaScript | 浏览器里的交互语言 | 页面能不能点、能不能动 |
| TypeScript | JavaScript 的加强版 | 更适合大型项目，错误更容易提前发现 |
| Vue / React | 前端框架 | 团队用来搭页面的一套工程方法 |
| Vben / Element Plus | 后台组件库 | 现成的表格、表单、弹窗、菜单 |

我们项目里前端常见组合是 **Vue 3 + Vben Admin + Element Plus + TypeScript**。听到这些词，不用记技术细节，只要知道它对应的是管理后台的页面体系。

### 后端常用

| 名字 | 是什么 | 你听到时可以理解为 |
|---|---|---|
| Python + FastAPI | 后端语言和框架 | 用 Python 写接口和业务逻辑 |
| Java + Spring Boot | 企业后端常见组合 | 银行、医院、政企系统里很常见 |
| Node.js | 用 JavaScript 写后端 | 适合轻量服务和实时应用 |
| Go | 高并发后端语言 | 适合流量大、性能要求高的服务 |

后端语言没有绝对好坏，更多看团队积累、客户环境、生态和招聘情况。FDE 不用参与语言之争，只要知道不同语言会影响开发效率和可维护性。

### 数据和部署常用

| 名字 | 是什么 | 你听到时可以理解为 |
|---|---|---|
| MySQL / PostgreSQL | 关系型数据库 | 存结构化业务数据 |
| Redis | 缓存数据库 | 把热数据放在内存里，读取更快 |
| Nginx | 流量入口 | 请求先经过它，再转到后端服务 |
| Docker | 打包运行环境 | 把程序和依赖装在一起，方便部署 |

## 大数据常用组件

做智能体项目躲不开数据，客户和研发一开口就是 Kafka、Flink、Doris、ClickHouse 这些词。你不用会搭，但得听得懂、知道各自管什么、什么时候该用哪个。

先记一个大分类，剩下的就好理解了：

- **消息队列**——数据的"传送带 + 缓冲区"，负责把数据从这头稳稳送到那头。代表：Kafka、RabbitMQ。
- **计算引擎**——负责"加工数据"，把原始数据算成指标、做清洗转换。分批处理（攒一批算一次）和流处理（来一条算一条）。代表：Flink、Spark。
- **分析型数据库**——专门存海量数据、做大范围统计查询的库，查得飞快。代表：ClickHouse、Doris。
- **同步工具**——把数据从一个系统搬到另一个系统。代表：SeaTunnel、DataX、Flink CDC。

### 消息队列（MQ / Kafka）

| 名字 | 是什么 | 你听到时可以理解为 |
|---|---|---|
| MQ（消息队列） | 一类中间件的统称 | 数据的排队缓冲区，削峰、解耦 |
| Kafka | 最主流的消息队列/数据管道 | 高吞吐的"数据传送带"，日志和实时数据都走它 |
| RabbitMQ | 传统消息队列 | 业务系统之间传消息，量没 Kafka 那么大时常用 |

**MQ 解决什么**：两个系统之间别硬连、别互相等。A 系统把消息扔进队列就不管了，B 系统有空再慢慢取。好处：

- **削峰**：一下子来 10 万条请求，先排队，后端按自己节奏处理，不会被冲垮。
- **解耦**：A 不用知道 B 在哪、活没活着，只管往队列扔。
- **缓冲**：下游挂一会儿也没事，消息还在队列里等着。

**Kafka** 是这类里的顶流，特别能扛（每秒百万条级），实时数据、日志、埋点、数据同步基本都用它当管道。客户说"数据先进 Kafka 再落库"，意思就是数据先上传送带缓冲，再由下游慢慢消费入库。

> 一句话：**MQ 是传送带，Kafka 是最能扛的那条传送带。** 什么时候需要——数据量大、要实时、多个系统要接同一份数据。医院这种数据量，多数场景其实用不上 Kafka，定时批量同步就够，别一上来就上。

### 计算引擎（Flink / Spark）

| 名字 | 是什么 | 你听到时可以理解为 |
|---|---|---|
| Flink | 流处理计算引擎 | 数据来一条算一条，秒级出结果 |
| Spark | 批处理为主的计算引擎 | 攒一大批数据一起算，适合离线报表 |
| Flink CDC | Flink 的一个能力 | 源库一改，实时捕获变更同步走（做准实时同步用） |

**计算引擎干的是"加工"的活**：数据抽过来是原始的，要清洗、关联、算成指标，这个加工过程数据量一大，就得靠计算引擎。

- **Flink** 擅长**流处理**——数据一到就立刻算，用在实时大屏、实时预警这类"必须秒级"的场景。
- **Spark** 擅长**批处理**——一批数据一起算，用在每天凌晨跑的离线报表、大规模数据清洗。

> 判断线：客户要"真·秒级实时"才需要 Flink；要的是"每天/每小时更新的报表"，Spark 或者更轻的定时任务就够。**别为了"实时"两个字上一套流处理，成本翻倍还难维护。**

### 分析型数据库（ClickHouse / Doris）

| 名字 | 是什么 | 你听到时可以理解为 |
|---|---|---|
| ClickHouse | 列式分析数据库 | 海量数据做聚合统计，快得离谱 |
| Doris（StarRocks 同类） | 国产分析型数据库 | 又快又相对好用，实时分析场景火 |

这类库和 MySQL/PostgreSQL 不是一路的。要分清两种库：

- **交易型库（OLTP）**：MySQL、PostgreSQL、Oracle。管日常业务读写——挂号、下单、改状态。一次动几条数据。
- **分析型库（OLAP）**：ClickHouse、Doris。管大范围统计——"过去一年全院各科室每天的门诊量和收入"，一次扫几千万上亿行做聚合。

**为什么要单独一种库**：拿业务库直接跑大统计查询会很慢、还拖垮业务系统。分析型库用"列式存储"等技术，专门优化聚合查询，同样一个报表查询可能快几十倍。

> 什么时候需要——数据量到千万、上亿行，报表越来越慢，就该考虑上分析型库。数据量不大时，PostgreSQL 加好索引、分好区就够了，别过度设计。ClickHouse 写入和更新有讲究，Doris 相对更均衡、国产化环境里更常见。

### 同步工具（SeaTunnel / DataX）

| 名字 | 是什么 | 你听到时可以理解为 |
|---|---|---|
| SeaTunnel | 开源数据集成引擎 | 配置一下就能把数据从 A 库同步到 B 库，几百种数据源现成 |
| DataX | 阿里开源的同步工具 | 老牌离线同步工具，同类用途 |

**干的是"搬运"的活**：把客户 HIS/EMR 里的数据抽出来，搬进我们的数仓。好处是**配置驱动、零代码**——填个数据源地址、表名、字段映射就能跑，不用为每个客户重写对接代码。我们的 SDR 就是拿 SeaTunnel 当底层同步引擎。细节见 [[大数据能力与医疗数据中台-学员材料]] 和 [[SDR标准数据仓库-学员材料]]。

### 放一起看：一条数据的旅程

把这些组件串起来，一条实时数据大致这么走（不是每个项目都全用上，按需取）：

```text
业务系统(HIS)
   ↓  同步工具(SeaTunnel/Flink CDC)抽取
消息队列(Kafka)           ← 缓冲、削峰
   ↓  计算引擎(Flink/Spark)加工清洗、算指标
分析型库(Doris/ClickHouse) ← 存好、供快速查询
   ↓  API / 语义查询
报表 / 驾驶舱 / 智能体
```

> **给 FDE 的定心丸**：这一整套是给"数据量巨大 + 要求实时"的场景准备的重装备。医院、政企多数项目的数据量（千万~亿行），一台好点的服务器 + PostgreSQL + 定时同步就扛得住，不用全套上齐。听到客户或研发提这些词，能对上号、能判断"这个场景到底要不要上"，就够了。

## 常见组件

组件可以粗分两类：前端组件和后端组件。

前端组件比较好理解，就是页面上重复使用的功能块：

- 按钮组件：统一样式、加载状态、禁用状态。
- 表单组件：输入框、下拉框、日期选择、校验规则。
- 表格组件：列表、分页、排序、筛选。
- 弹窗组件：新增、编辑、确认、查看详情。
- 图表组件：折线图、柱状图、饼图。

后台管理系统看着页面很多，其实大部分都是“查询区 + 表格 + 弹窗表单”的组合。所以研发说复用组件，意思不是偷懒，而是把同类页面标准化，后面改一处就能全局生效。

后端组件更像一套基础设施，常见这些：

- **认证组件**：判断你是谁，常用 JWT、Token、单点登录。
- **权限组件**：判断你能干什么，控制菜单、按钮、接口、数据范围。
- **缓存组件**：把经常查的数据先存起来，减少重复计算。
- **消息队列**：把耗时的活先排队，比如批量导入、生成报告、发送通知。
- **对象存储**：放文件、图片、PDF、音频这类非结构化内容。
- **日志组件**：记录系统运行情况，排查问题时靠它。
- **监控告警**：服务挂了、接口变慢、错误变多时提醒运维和研发。

在智能体项目里还会多几类：

- **向量库**：存知识库切片后的语义向量，用于检索。
- **RAG 检索组件**：先查资料，再让模型基于资料回答。
- **模型网关**：统一管理模型调用、限流、计费和降级。
- **Agent 编排组件**：决定智能体按什么步骤干活、调用哪些工具。

## 常见架构

架构听起来很大，其实就是回答几个问题：程序怎么拆、部署在哪、数据怎么隔离、流量怎么走。

### 前后端分离

现在的管理系统基本都是前后端分离。前端独立开发和部署，通过 API 调后端；后端只负责数据和业务逻辑。

好处是分工清楚，前端可以并行做页面，后端可以并行做接口。代价是两边必须先把 API 约定好，否则会互相等。

### 单体架构

所有功能放在一个后端服务里，用户管理、订单、报表、权限都在同一个程序里。

适合早期项目和团队规模小的情况。优点是简单、好部署、排查问题集中；缺点是功能多了以后，一个小改动也可能影响整个系统。

### 微服务架构

把系统拆成多个独立服务，比如用户服务、订单服务、支付服务、智能体服务、知识库服务。

好处是各模块可以独立发布和扩容；代价是部署、监控、联调都更复杂。没有足够运维能力时，盲目拆微服务反而会增加成本。

### SaaS 多租户架构

SaaS 是一套系统服务很多客户。多租户就是每个客户的数据要隔离开，A 医院看不到 B 医院的数据。

常见隔离方式有三种：

- 共享库共享表：成本低，靠字段区分租户。
- 共享库独立 Schema：隔离中等，管理复杂一点。
- 独立数据库：隔离最好，成本最高。

FDE 听到“多租户”时，重点问数据隔离、定制配置、权限边界，不用纠结底层实现。

### 私有化部署

私有化部署是把系统装在客户自己的机房或指定云环境里。优点是数据留在客户侧，容易满足安全要求；代价是版本升级、环境适配、运维成本都会变高。

医疗行业常见混合形态：业务系统本地部署，部分 AI 能力调云上 API。这时就要提前确认网络、带宽、数据出境和合规要求。

### AI 应用常见分层

智能体应用通常会分成几层：

```text
用户入口层：Web 页面 / App / 企微入口
应用服务层：业务逻辑、权限、会话管理
Agent 编排层：Prompt、工具调用、流程控制
知识检索层：知识库、向量库、RAG
模型服务层：大模型、Embedding、重排模型
数据存储层：业务数据库、文件存储、日志
```

产品评审时可以按这个层次问：入口在哪里、数据怎么管、智能体怎么编排、知识从哪来、模型怎么选。这样问下来，基本不会漏掉大结构。

## 环境、联调和发布

研发说“代码跑起来了”，你要接着问一句：在哪个环境跑起来？

常见环境大概有这几类：

| 环境 | 给谁用 | 作用 |
|---|---|---|
| 本地环境 | 研发自己 | 在自己电脑上写代码、调试 |
| 开发/测试环境 | 研发和测试 | 联调接口、提测、修 bug |
| 预发/验收环境 | 产品和客户 | 用接近线上的配置做验收 |
| 生产环境 | 真实用户 | 正式对外提供服务的环境 |

不同环境的账号、数据、网络、配置都可能不一样。所以“测试环境没问题，线上有问题”很常见，不一定是研发乱讲。

几个词也顺手记住：

- **联调**：前端接后端真实接口，不是各改各的。
- **提测**：研发自测完成，交给测试正式测。
- **冒烟测试**：先跑最核心路径，登录、下单、生成报告这些。
- **回归测试**：新功能上线前，把老功能再测一遍。
- **灰度发布**：先放一小部分用户用，稳定后再全量。
- **回滚**：新版本出问题，先退回上一个稳定版本。

FDE 不用管发布命令，但发布前要确认几件事：数据库脚本有没有执行、配置是否改好、第三方服务是否可用、上线后怎么验证、出问题能不能回滚。

## FDE 容易漏的非功能需求

功能需求是“能做什么”，非功能需求是“做得稳不稳、安全不安全、出了问题怎么办”。这类需求最容易在评审时被略过，上线后最容易挨骂。

### 性能

不要只说“页面要快”，尽量给出场景：

- 列表 1 万条数据时，加载多久可以接受？
- 并发 100 人提交时，会不会卡死？
- 生成一份报告要多久，等待过程能不能离开页面？
- 大文件上传失败后，能不能断点续传？

### 可用性

想清楚依赖挂了怎么办：

- 模型服务超时，能不能提示稍后重试？
- 第三方接口挂了，本地流程还能不能继续？
- 数据库慢查询导致页面卡住，有没有降级方案？

### 安全和权限

至少问这几条：

- 谁能看这份数据？
- 谁能导出、删除、修改？
- 接口是不是只校验了页面按钮，没校验权限？
- 多租户数据有没有隔离？
- 密码、身份证号、手机号有没有脱敏？

### 审计和日志

关键操作要有记录：谁在什么时间改了什么、改前改后是什么。医疗、政企项目里，这块经常是验收重点。

### 兼容性

- 要支持哪些浏览器？
- 手机端要不要适配？
- 最低支持什么分辨率？
- 老版本接口要不要继续兼容？

这些看起来不像“功能”，但都会影响开发量和排期。评审时不问，研发就按默认做法做，最后容易和预期不一致。

## 需求评审时可以问的问题

- 这个功能的数据从哪里来？
- 要新增或修改哪些字段？
- 哪些角色能看、能改、能删？
- 前后端接口有没有约定好？
- 加载中、空数据、报错时分别显示什么？
- 有没有历史数据要迁移？
- 部署在云上还是客户本地？
- 这次验收用的是真实数据还是假数据？

这些问题不用装懂技术，问出来反而能让研发觉得你靠谱。

## 和智能体项目的关系

在我们现在的智能体项目里，前后端代码只是载体。前端负责工作台页面，后端负责接口、权限和数据流转，但真正决定产品价值的是智能体本身：Prompt 怎么写、知识库怎么建、工具怎么编排、效果怎么评测。

所以看一个智能体平台，别只看页面漂亮不漂亮，要问三件事：

- 数据有没有打通？
- 智能体有没有按标准流程设计？
- 上线后有没有真实使用和反馈闭环？
